# RAGForge AI

Document question answering over user-provided PDFs and web pages using
retrieval-augmented generation (RAG).

## Overview

A user provides a PDF or a website URL. The application extracts and
chunks the text, embeds it, and builds an in-memory vector index scoped
to that one source. Questions are answered by retrieving the most
similar chunks from the *currently loaded* source only, passing them to
a local instruction-tuned model, and returning the generated answer
alongside deterministic page/URL citations built from the retrieved
chunk metadata — never generated by the model itself.

Follow-up questions are supported: a short conversation history is kept
per session and used only to rewrite an ambiguous follow-up ("what
parameters does it use?") into a standalone query — never as a source of
facts, so every answer is still grounded in retrieval against the active
document. Loading a new PDF or URL replaces the active index and resets
the conversation; there is no cross-document leakage between sources
loaded in the same session (see `evaluation/experiments.md`, Task 4).

## Features

- PDF question answering (upload and ask)
- Website question answering (URL and ask)
- Per-session document isolation — switching sources replaces the
  retrieval index and resets conversation history
- Follow-up question handling via query rewriting, without treating
  conversation history as a factual source
- Deterministic page/URL source attribution, built from retrieved chunk
  metadata (not generated by the LLM)
- Unsupported-query rejection via a cosine-similarity relevance
  threshold (with a documented limitation — see Evaluation)
- Streamlit chat interface
- CPU/GPU-adaptive generation loading (no code change required either way)
- An evaluation suite with a historical and an expanded benchmark,
  covering retrieval, generation, and negative-query rejection

## Architecture

```
User
  ↓
PDF / Website
  ↓
Ingestion (extract text, chunk, embed)
  ↓
FAISS IndexFlatIP  (per-session, in-memory)
  ↓
Similarity threshold (0.25)
  ↓
Contextual query rewrite   ←  conversation history (last few turns)
  ↓                             (used only to resolve "it"/"this", never as a fact source)
Grounded prompt  ←  retrieved chunks only
  ↓
Qwen2.5-1.5B-Instruct
  ↓
Answer + deterministic sources  ←  retrieved chunk metadata (page, source)
```

Two points worth being explicit about, since they're easy to get wrong in
a RAG app with memory: conversation history only ever changes *how the
query is phrased* before retrieval, never the factual content of the
answer; and source citations are assembled programmatically from the
retrieved chunks' own `source`/`page` fields (`src/rag.py:build_sources`)
— the model is never asked to produce them, and its output is never
parsed for them.

## How It Works

### Ingestion

**PDF**: extract text page-by-page (PyMuPDF) → split into 100-word
chunks with 20-word overlap → embed each chunk (MiniLM, L2-normalized) →
build a fresh FAISS `IndexFlatIP` for that document.

**Website**: fetch the page → strip `script`/`style`/`nav`/`footer`/
`header`/`aside`/`form`/`noscript` → reject pages with too little
remaining text or a failed/invalid request, with a specific error
message rather than a generic crash → chunk/embed/index the same way as
a PDF.

Both paths return a fresh `(index, chunks)` pair; nothing is written to
a shared file, so there's no risk of one session's document leaking into
another's.

### Querying

1. If there's prior conversation history, rewrite the question into a
   standalone form using the same generation model (no second model).
2. Retrieve the top 10 chunks from the current document's index.
3. Drop any result below the 0.25 similarity threshold; if nothing
   remains, return a fixed "could not find the answer" response with no
   sources.
4. Build a prompt from the surviving chunks and generate an answer.
5. Attach deterministic sources built from those same chunks (deduped,
   ordered by retrieval relevance).

The active index, chunks, source name, and conversation history all live
in Streamlit's `session_state` — there is no database and no shared
application-level state between browser sessions.

## Evaluation

Two benchmark populations exist and are **not directly comparable** —
the expanded set is deliberately harder and covers more question types,
so its numbers should not be read as a regression from the historical
set.

### Historical benchmark (10 positive + 5 negative questions)

| Metric | Value |
|---|---|
| Recall@1 / @3 / @5 / @8 / @10 | 0.500 / 0.900 / 0.900 / 1.000 / 1.000 |
| Generation keyword coverage | 0.757 |
| Generation semantic similarity | 0.787 |
| Negative-query rejection | 5/5 (100%) |

### Expanded benchmark (28 positive + 12 negative questions)

| Metric | Value |
|---|---|
| Recall@1 / @3 / @5 / @8 / @10 | 0.321 / 0.643 / 0.750 / 0.821 / 0.893 |
| Generation keyword coverage | 0.708 |
| Generation semantic similarity | 0.619 |
| Negative-query rejection | 0/12 (0%) |

Both benchmarks are run against the same production configuration:
100-word/20-word-overlap chunking, `all-MiniLM-L6-v2`, FAISS
`IndexFlatIP`, threshold 0.25, top_k 10, no reranking,
`Qwen/Qwen2.5-1.5B-Instruct`.

### Important finding: the threshold is a topic filter, not a fact filter

The historical 5 negative questions ("What is the capital of France?",
etc.) are topically unrelated to the corpus and score far below 0.25
(around 0.02 similarity) — trivial to reject. The 12 expanded negatives
were written to be realistic instead: plausible questions about the
loaded document (dataset size, sensor location, who the mentor is) that
the document simply never answers. Because they share vocabulary with
the corpus, they score 0.32–0.54 — **above** the threshold — and **none
of the 12 were rejected**.

In other words: the current similarity gate reliably tells "this
document is about a completely different topic" apart from "this
document is about the right topic," but it cannot tell "this document is
about the right topic" apart from "this document actually answers this
specific question." That's a real, unresolved limitation, not something
this project claims to have solved — see Future Work.

## Experiments

Full write-ups, including rejected approaches, are in
`evaluation/experiments.md`. Summary of experiments with recorded,
reproducible results:

| Experiment | Result | Decision |
|---|---|---|
| Baseline retrieval (chunk100, `IndexFlatIP`, no threshold) | Recall@1 0.500, Recall@3/5 0.900, MRR@3 0.683 | Starting point |
| Threshold calibration (0.00–0.40) | 0.25 keeps Recall@3 at 0.900 and rejects 5/5 negatives; 0.40 drops Recall@3 to 0.700 | Selected 0.25 |
| Cross-encoder reranking | Retrieval improved (Recall@1 0.500→0.800, MRR@3 0.683→0.833), but generation keyword coverage fell to 0.522 (top-3) / 0.581 (top-5) from 0.742 | Rejected — not used in production |
| Prompt-only rule change (Q7 investigation) | Keyword coverage 0.721→0.667, semantic similarity 0.751→0.733; the model ignored the added rule while other answers regressed | Rejected, reverted |
| Semantic similarity metric added | New metric alongside keyword coverage; disagreed with it in informative ways (e.g. flagged a keyword-rich but off-target answer) | Kept as a second signal |
| Retrieval candidate depth 5 → 10 | On this project's own validation benchmark: generation keyword coverage 0.721→0.757, semantic similarity 0.751→0.787, Recall@5 0.900→1.000 (at k=8/10) | Kept, promoted to production (`top_k=10`) |

The reranking result is experiment-only — `src/reranker.py` exists and is
exercised by evaluation scripts, but `src/rag.py` never calls it. The
candidate-depth improvement is reported as an improvement on this
project's own benchmark, not a universal result.

Either benchmark can be re-run with `python evaluation/evaluate_retrieval.py`
/ `evaluate_generation.py` (historical, default) or with an `expanded`
argument; results are written to separate files so neither overwrites
the other, and historical results stay reproducible.

## Limitations

- Both benchmarks (10+5 and 28+12 questions) are small; results may not
  generalize to arbitrary documents.
- The similarity threshold rejects off-topic questions reliably but not
  plausible-sounding, unsupported ones — demonstrated directly by the
  0/12 rejection rate above.
- Generation quality depends on retrieval quality: when the right chunk
  isn't retrieved, the model can produce a fluent but incorrect answer
  instead of declining.
- Website extraction depends on the page's own HTML structure; a minimum
  text-length check rejects the most degenerate cases, but unusual page
  layouts can still yield thin or unreliable text.
- The generation model (Qwen2.5-1.5B-Instruct) is a small instruction
  model and doesn't reliably follow nuanced prompt instructions — shown
  directly by the rejected Q7 prompt experiment above.
- One active document per session, held in Streamlit `session_state`;
  there is no persistent storage, multi-user state, or database.

## Setup

**Requirements**: Python 3.10+ (the codebase uses `list[dict]` / `X |
None` type syntax). A CUDA GPU speeds up generation but isn't required —
`src/generator.py` falls back to CPU automatically.

```bash
python -m venv .venv
.venv\Scripts\activate        # Windows
source .venv/bin/activate     # Linux/macOS

pip install -r requirements.txt
```

### Run

```bash
python -m streamlit run app.py
```

### First run

The embedding model (`all-MiniLM-L6-v2`) and the generation model
(`Qwen/Qwen2.5-1.5B-Instruct`) are downloaded automatically by
`sentence-transformers`/`transformers` the first time they're used, and
cached under `~/.cache/huggingface`. This needs a working internet
connection once; exact download size isn't pinned here since it depends
on the model revision Hugging Face serves.

## Usage

1. Start the app (`python -m streamlit run app.py`).
2. In the sidebar, choose **PDF** or **Website**.
3. Upload a PDF or enter a URL, then process it.
4. Ask a question in the chat box.
5. Read the answer and the sources listed beneath it.
6. Ask a follow-up — it's interpreted using the recent conversation.
7. Load a different PDF or URL to switch documents; this resets the
   conversation, since it's scoped to the previously active source.

## Configuration

These are implementation constants in `src/rag.py`, not environment
variables — there's no `.env` setting that changes them:

- Relevance threshold: `0.25`
- Retrieval depth: `top_k=10`

The only environment variable the project reads is optional:

- `HF_TOKEN` — raises Hugging Face Hub's anonymous rate limit for model
  downloads. See `.env.example`. The app works without it.

## Testing

```bash
python -m unittest discover -s tests
```

50 tests across 7 files: document ingestion and per-session isolation,
website extraction robustness (bad URLs, HTTP failures, empty pages),
conversation memory (follow-up resolution, cross-document isolation
under a simulated caller bug), source-attribution/provenance (dedup,
ordering, missing metadata), Streamlit UI behavior via
`streamlit.testing.v1.AppTest`, deployment-readiness regressions (no
hard-coded GPU device or local paths), and expanded-benchmark validation
(gold chunk references, no duplicate questions). No test requires
network access or downloads a model beyond what's already cached.

## Future Work

The strongest next step: **improve unsupported-query detection beyond a
single similarity threshold** — the expanded benchmark shows the current
gate can't distinguish "topically related" from "actually answered."
Other realistic directions:

- Grow the evaluation benchmark further, and across more source documents
- Lightweight evidence verification (does the retrieved context actually
  entail the requested fact, not just relate to it)
- Improved citation UX (e.g. linking directly to the source page/chunk)
- More robust website extraction across a wider range of page structures
- Deployment to a hosted environment
- Evaluating a larger or stronger generation model
